01

Hardware architecture

Each RTD gets its own MAX31865 converter on a shared SPI bus — this is what makes ±0.5 °C reachable with 1 m PT100 leads: 3-wire compensation cancels lead resistance per channel in hardware instead of needing firmware calibration.

02

Firmware logic

One sweep of all eight channels every 10 s, connected or not, then queued for upload. Once reconnected, the backlog drains one row per cycle alongside live data instead of dumping all at once.

Backlog capacity Each queued row is date-time + 8 channel readings ≈ 40 bytes; at the 10 s sample interval that's 14.4 KB/hour of backlog growth. The N8R2's 2 MB PSRAM comfortably holds the queue — budgeting ~1.6 MB to it (leaving headroom for Wi-Fi/TLS buffers and heap fragmentation) gives 40,000 rows, or ~111 hours (~4.6 days) of Wi-Fi outage before the buffer fills and the oldest unsent rows start being dropped. Every queued row is also written to the flash's LittleFS partition (up to 36,000 rows, ~100 hours), so a power cut or reset no longer loses the backlog: it is reloaded at boot and sent once Wi-Fi is back. Flash is written only while rows are queued, so normal operation causes no wear.
Decided Mains-powered, so there's no reason to deep-sleep between sweeps — the ESP32-S3 stays awake with a persistent Wi-Fi connection and holds a fixed 10 s wait between cycles, whether or not Wi-Fi is up, which comfortably tracks equipment/process temperatures without flooding the server. Under normal (connected) operation the backlog queue stays empty; it only fills during an actual outage.

04

Cloud upload payload

MQTT over TLS to AWS IoT Core, QoS 1. One message per reading on the topic rtd/<device_id>/telemetry: each 10 s cycle sends the live reading and, while draining a backlog, one queued reading as a second message.

FieldTypeRequiredNotes
topic string yes rtd/<device_id>/telemetry. The device id is taken from the topic, never from the body, and the IoT policy only lets a certificate publish to its own topic
fw_version string yes Current firmware version — lets the server correlate readings with what's running, and target OTA pushes later
backlog integer no Rows still queued on the device once this message is delivered; the dashboard shows it and the time left to catch up
ts string yes ISO 8601, UTC — the full date+time the row was sampled; a backlog row keeps its original time
channels[] array yes Always 8 entries, ch 1–8 in fixed order
channels[].ch integer yes 1–8, matches the physical channel/terminal number
channels[].type string yes "PT100" (ch 1–7) or "PT1000" (ch 8)
channels[].temp_c number yes Degrees Celsius, 2 decimal places; null when the MAX31865 reports a fault on that channel
Delivery The broker's PUBACK is the "delivered" signal: the firmware drops a row from its queue (RAM and flash) only after it, and otherwise keeps it and sends it again. The server stores each row once, de-duplicated by device and timestamp, so a re-send is harmless; it acknowledges malformed messages too, so one bad row can never block the backlog, and it leaves a message unacknowledged only if storing it failed. A row timestamped before 2024 or more than a day ahead is discarded. fw_version is in the schema now so it's already there when OTA lands later. The server still has an HTTPS /ingest endpoint with a bearer token for testing.
